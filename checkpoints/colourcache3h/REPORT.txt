WHY THIS CHANGE
The 15:57:11 NATIVENORM3G PHOTO capture used native normalization successfully:
  normalization 262.135 ms (previous 3F observation 1303.349 ms)
  renderer 2302.470 ms; save branch through pre-sidecar 3223.511 ms
  native colour/tone 1026.828 ms; AMaZE initialization + bands 741.837 ms
  JPEG and DNG saved, exactly one photographic RAW, no fusion/HDR.
Exposure was delivered exactly as requested: ISO 250, 38.88 ms. No original RAW
sites reached white. Different captures/device states make these observations,
not controlled benchmarks. MOTION still needs a phone capture.

The native colour loop's final TONECAL1A function accepts an already quantized
RGB24 value and calculates fixed Lab lightness calibration, including cube roots
and powers. Repeated RGB values produce identical results. This checkpoint adds
exact-key memoization of that function, preserving its original arithmetic on
all misses. No colour, exposure, white-balance, tone or sharpening parameter is
changed. There is no interpolation or approximate lookup table.

IMPLEMENTATION
Each of the existing four band workers owns 16,384 direct-mapped cache entries:
  131,072 bytes of entries per worker; at most 524,288 bytes across four workers.
The cache lives on that worker's stack and resets for each band. It stores the
complete RGB key plus a validity tag and calibrated RGB output. Hash collisions
are misses and call the original function. Alpha is preserved independently.
No cache data survives a render or is shared between workers.

The original native pixel-loop text is identical except for the final calibration
call. All original native helper functions are unchanged. Native diagnostics
retain their full-frame counters. The new isolated m10rcolour3h library contains
the colour loop and cache; original dngCreator and all 25 parent native libraries
remain byte-identical. All assets also remain byte-identical. The cache uses
private statically linked C++ runtime symbols so the packaged shared runtime is
not replaced. Both existing ABIs are built: arm64-v8a and armeabi-v7a. ELF and ZIP
16 KiB alignment were checked. No device-model or lens-specific dispatch.

M10R_TONE_CACHE3H defaults true. -Pm10rToneCache3H=false selects the existing 3G
native colour path. Missing-library/missing-symbol or rejected-input cases use
that same parent path. Out-of-memory errors and native crashes are not disguised
as a successful fallback. Existing native normalization3G, exposure policy,
AMaZE, DETAIL3D and PHOTO/MOTION routing are preserved. DETAIL3D remains enabled
in this test APK and false by default in source builds.

These single host runs suggest roughly 15–21% lower colour-stage time, but are
not predictions of Android speedup or total capture time. CPU scheduling, cache
behaviour, JNI copying, compiler/libm and scene colour diversity differ. Scenes
with few repeated colours may benefit less or pay cache overhead. Host equality
is not proof of ARM output bit parity against the already-shipped binary.

Compare rendererTiming3E.nativeColourAndTone with prior observations. The object
