# M10-R Exposure Engine v0.12: Traditional Meter Cadence and Negative-Bv Delay

**Date:** 2026-09-04  
**Firmware:** `M10-R-30.22.23.34-Customer.FW`  
**Original FW SHA-256:** `ec8df72dc7d4c90332abb3cdbc07c6db837ffed802c1a9712b6f3d6e0edf6498`  
**Decoded SHA-256:** `859c936b6ac8efe0bc4ce7f05623013644fc5d8aee3c6835f09860f452adc2e0`

## 1. Outcome

This pass closes the outer scheduling boundary around the traditional/rangefinder meter sufficiently for the host-side model.

The traditional 10-sample ADC measurement is not a shutter-only operation. The final-Bv selector is invoked from an exposure-event consumer, and that consumer receives a periodic event-bit-0 update generated by a scheduler callback. The periodic callback uses an internal tick counter and posts the metering/exposure update whenever:

```text
(counter * 10) % 100 == 0
```

Thus the exposure-update event is generated every ten callback invocations. The repeated `counter * 10` arithmetic is strongly consistent with a 10-ms base scheduler tick and therefore a 100-ms metering/exposure-update cadence. The 100-ms cadence is instruction-level. Calling the underlying scheduler period exactly 10 ms remains a strong static inference because the firmware does not expose a symbolic `10 ms` name at this boundary.

The 300-ms negative-Bv mechanism is also closed: it does not suspend ADC sampling. A negative traditional Bv sets a latch and arms a scheduler timer for `0x12C = 300`; the registered timer callback clears the same latch. The latch therefore delays traditional-Bv eligibility/source acceptance while metering/update activity can continue.

## 2. Final-Bv selector has one direct production caller

`0x0800D6A8` has one direct call site in CTRL-System:

```text
0x0800DD28 -> BL 0x0800D6A8
```

This sits in the exposure-event consumer beginning at `0x0800DCC6`.

Relevant event-consumer behavior:

```text
wait/read exposure event object
...
if event bit 0 is set:
    if local/global eligibility gate permits:
        changed = final_bv_selector()
        copy changed into event bit 1

if event bit 1 is set:
    if downstream state permits:
        build exposure input / run calculator
```

The final-Bv selector is therefore event-driven rather than called directly from the shutter-button state machine.

## 3. Selector performs synchronous traditional measurement

Within `0x0800D6A8`, each branch that chooses a live source invokes selector `5` synchronously before reading the chosen Bv state:

```text
0x0800D6EE -> 0x080184D8(selector=5)
0x0800D718 -> 0x080184D8(selector=5)
0x0800D73C -> 0x080184D8(selector=5)
```

The selector-5 constructor is the already-recovered traditional-meter acquisition path. It performs the ADC/Tlog acquisition and dispatches the local 9-byte AE-measure result before the final-Bv selector continues.

Thus a periodic final-Bv update does not merely inspect a stale independently-running meter value. It can synchronously cause a fresh traditional measurement.

## 4. Periodic event-bit-0 producer

One direct producer of exposure event mask `1` is:

```text
0x0801057E -> BL 0x0800DC4A
```

It lives in scheduler callback `0x080104B8`.

The callback maintains a halfword counter. The relevant block is:

```text
counter_value = state_counter
scaled = counter_value * 10

if scaled % 100 == 0:
    post_exposure_event(mask=1)
```

The same callback performs several other time-divisor checks using the same `counter * 10` coordinate, including divisors corresponding to `1000`, `250`, `100`, `30`, and `20`.

At the end it increments the counter by one.

### Timing interpretation

The exposure event therefore occurs every ten callback invocations.

The repeated multiplication by ten before all time-like modulus tests strongly indicates that one callback invocation represents 10 ms. Under that interpretation:

```text
callback cadence       ~= 10 ms
meter/exposure update  = 100 ms
```

The second line is the practical production model to preserve. The first line should remain labeled a strong static inference until a named scheduler period, RTOS timer configuration, or hardware trace confirms it directly.

## 5. Callback is scheduler-registered

The callback appears as Thumb pointer:

```text
0x08039A78 = 0x080104B9
```

in a static callback/state registry. The immediately following word is its state slot:

```text
0x08039A7C = 0x2001ADC2
```

Nearby entries use the same callback/state pairing pattern:

```text
0x08039A80 = 0x080106A5
0x08039A84 = 0x2001ADC3
0x08039A88 = 0x08010741
0x08039A8C = 0x2001ADC4
0x08039A90 = 0x0801079D
0x08039A94 = 0x2001ADC5
0x08039A98 = 0x08010675
0x08039A9C = 0x2001ADC6
0x08039AA0 = 0x08010775
0x08039AA4 = 0x2001ADC7
```

This confirms that both the periodic update callback and the negative-Bv expiry callback participate in the same scheduler/timer callback infrastructure.

## 6. Negative-Bv timer lifecycle

Function `0x0800E16C` is the negative-traditional-Bv check:

```text
Bv = traditional_Bv_get()
if Bv < 0:
    negative_Bv_latch = 1
    arm_timer(300)
```

Instruction sequence:

```text
0800E16E  BL   0x08011D7A   ; traditional Bv getter
0800E172  CMP  r0,#0
0800E174  BPL  done
0800E176  MOVS r0,#1
0800E178  BL   0x0800E166   ; latch setter
0800E17C  MOV.W r0,#0x12C   ; 300
0800E180  BL   0x0801077E   ; timer arm
```

The timer arm routine `0x0801077E` hands the duration to the scheduler/timer service.

Its paired callback is `0x08010774`:

```text
08010774  PUSH {r7,lr}
08010776  MOVS r0,#0
08010778  BL   0x0800E166   ; same latch setter
0801077C  POP  {r0,pc}
```

Therefore expiry performs exactly:

```text
negative_Bv_latch = 0
```

The callback pointer is registered at `0x08039AA0` with state slot `0x2001ADC7`.

## 7. What the 300-ms latch does and does not do

The latch is consulted inside `0x0800D6A8` when deciding whether the calibrated traditional-Bv path may be selected.

The latch does **not** sit in the ADC acquisition loop and does not disable the periodic exposure-event producer.

Therefore the correct abstraction is:

```text
periodic update event
    -> final-Bv selector
        -> meter acquisition may continue
        -> source/acceptance logic checks negative-Bv delay latch
```

not:

```text
negative Bv
    -> stop meter for 300 ms
```

This distinction matters for a replica because stopping the phone luminance estimator for 300 ms would produce different recovery and lock behavior.

## 8. Meter/update cadence model

For a deterministic host implementation, the practical model is:

```text
while metering subsystem active:
    every ~100 ms:
        acquire fresh traditional meter sample set
        update Tlog / traditional Bv / BvExt-related state as available
        run final-Bv source selection and deadbands
        if final-Bv/update state changed:
            request exposure recalculation
```

Separately:

```text
if newly processed traditional Bv is negative:
    negative_Bv_delay_latch = true
    schedule latch clear for +300 ms

on expiry:
    negative_Bv_delay_latch = false
```

AE lock remains downstream of this process and freezes the allocator's cached calculation Bv rather than stopping the 100-ms metering loop.

## 9. Relationship to first-detent AE lock

This timing result reinforces v0.07/v0.08:

- metering is a recurring event-driven process;
- the first shutter detent sets AE lock downstream;
- the lock-triggered calculation cannot synthesize a special final unlocked meter refresh;
- already-scheduled/periodic meter activity is conceptually separate from the allocator cache freeze.

For the phone replica, do not perform a special meter read merely because first detent was pressed. Freeze the allocator cache when the lock transition is processed and let the normal meter loop continue upstream.

## 10. Remaining timing questions

The highest-value remaining timing details are now narrower:

1. Identify the exact enable/disable lifecycle of scheduler callback `0x080104B8` (when metering starts/stops with camera state).
2. Resolve the local/global gate at `0x0800DD1E..0x0800DD28` that can suppress the selector even when event bit 0 is pending.
3. Determine whether release state changes force an immediate mask-1 update in addition to the periodic cadence.
4. If exact hardware parity is eventually required, confirm the inferred 10-ms scheduler base experimentally or through the timer service configuration.

These are refinements around a now-stable production abstraction rather than blockers for the offline exposure oracle.
